How it works

One callback per packet.
The library does the rest.

The processing pipeline is a simple loop — global init, handler setup, packet processing, teardown.

  1. init_extraction()

    Global state — once, before any handler. Sets up registries, allocators, and protocol tables.

  2. mmt_init_handler()

    One handler per packet stream. Specify the data-link type (DLT_EN10MB for Ethernet) and get back a handler for registration.

  3. Register attributes + callback

    Call register_extraction_attribute_by_name() for each field you want, then register_packet_handler() with your callback.

  4. packet_process() loop

    One call per captured packet. The library classifies, extracts, tracks sessions, and invokes your handler.

  5. mmt_close_handler() then close_extraction()

    Teardown in reverse order: handler first, then global state. Every path — normal and error — follows this sequence.

packet_handler.c 
// 1. Global init
if (!init_extraction()) return 1;

// 2. One handler per stream
mmt_handler_t *h = mmt_init_handler(DLT_EN10MB, 0, errbuf);

// 3. Register what you need
register_extraction_attribute_by_name(h, "META", "PACKET_LEN");
register_packet_handler(h, 1, on_packet, NULL);

// 4. Process loop
while (pcap_next_ex(...) == 1) {
    packet_process(h, &header, data);
}

// 5. Teardown: handler, then global
mmt_close_handler(h);
close_extraction();
API reference

Five core functions.
One processing loop.

The public API is intentionally small. Everything flows through these entry points.

mmt_core.h
int init_extraction(void);

Returns 1 on success, 0 on failure. Must be called once before any handler. Sets up protocol registries, the session table, and the arena allocator.

mmt_core.h
mmt_handler_t* mmt_init_handler(
    uint32_t dlt,
    uint32_t flags,
    char *errbuf
);

Creates a handler for one packet stream. dlt is the data-link type (e.g. DLT_EN10MB). flags controls optional features. Returns NULL on failure.

mmt_core.h
int register_extraction_attribute_by_name(
    mmt_handler_t *handler,
    const char *proto,
    const char *attr
);

Register a protocol attribute to be extracted. proto and attr are the canonical names (e.g. "META", "PACKET_LEN"). Returns 1 on success.

mmt_core.h
int packet_process(
    mmt_handler_t *handler,
    struct pkthdr *hdr,
    const u_char *data
);

The core processing function. Classifies the packet, extracts registered attributes, tracks sessions, and invokes registered packet handlers. Returns 1 on success.

mmt_core.h
void mmt_close_handler(mmt_handler_t *handler);
void close_extraction(void);

Teardown in reverse order: close each handler, then call close_extraction(). Every code path — including error paths — must follow this sequence.

FAQ

Common questions.

What platforms are supported?

Linux distributions: Debian/Ubuntu, Fedora/RHEL, Arch, Alpine, and openSUSE. Pre-built .deb and .rpm packages are available on the Releases page. The library itself compiles on any Linux with GCC 9+.

Can I add custom protocols?

Yes. MMT-DPI uses a plugin architecture — write a shared library that registers a protocol classifier, attribute extractors, and optional session handlers. No core changes needed.

Is it thread-safe?

Yes. Each mmt_handler_t is independent. You can process packets from multiple threads, each with its own handler. Global init/teardown functions must be called once.

How does it handle encrypted traffic?

MMT-DPI classifies traffic by payload patterns, protocol headers, and behavioral heuristics — not by port numbers. Even TLS-encrypted flows are classified by their handshake patterns and application-layer signals.

What's the licensing?
